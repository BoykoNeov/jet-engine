Slice V step 4 (2026-08-25) shipped `dump_slice_v.py` + both goldens +
`slice_v_oracle.rs`: 6 819 keys, bit-exact vs PyPy first run and vs CPython 3.14 with
0 drifts and 0 flips. Four process lessons, all of which cost something:

**A stale field's reach is a property of WHERE IN A READER CHAIN you look.** Step 3
measured the carrier bug's `margin_min_lp` channel as not moving and booked 15.4 % forward
to step 5. It had probed `transient_surge_margin_fuel`, which re-marches from
`equilibrium` and re-arms before anything stale can arrive. The reader ONE CALL EARLIER in
the same chain moves 15.431 % exactly. *A channel measured closed at one reader says
nothing about the reader before it* — so name the reader when recording a null result.

**Fixing an instance of a failure mode is not sweeping for it.** I fixed a guessed
relative tolerance (the plan prints SIGNIFICANT figures, so the licence is half a unit in
each value's own last printed DECIMAL place — per-value, not a constant) and then shipped
the review with the identical defect still sitting in the next gate down, as `n > 400` on
a measured 516. After fixing a guessed bar, re-read every other bar in the same file.

**An oracle catching a bug does not retire the gate written for that bug.** The oracle
detects the carrier injection at 87 keys, but a golden-comparison gate is defeated by
regenerating the golden against buggy code; a gate that MANUFACTURES the bug inline is
not. Write the non-overlap down, or the later step inherits a discharged-looking IOU.

**A provenance claim needs a provenance record.** The two goldens were byte-identical,
which is the interesting result — and is also exactly what two files from the SAME
interpreter look like. The dump now stamps `# generated by <impl> <version>` and the
comparator skips `#` lines.

Also: `1.4 - 1.0` is `0.3999999999999999`, not `0.4`. Spelling `R_c` the second way put the
first go/no-go 48 ULPs off § 5.20 (ii)'s bits.
